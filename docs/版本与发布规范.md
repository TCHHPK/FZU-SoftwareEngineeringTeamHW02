# 版本与发布规范

> 适用范围：本项目所有对外发布的代码包、部署版本与 GitHub Release。
> 依据：[语义化版本 2.0.0](https://semver.org/lang/zh-CN/) + [Keep a Changelog 1.1.0](https://keepachangelog.com/zh-CN/1.1.0/)

## 一、版本号格式

```
主版本号 . 次版本号 . 修订号
   X    .   Y     .   Z
```

| 位 | 何时升 | 判定标准 | 举例 |
| --- | --- | --- | --- |
| **X 主版本** | 不兼容改动 | 接口路径/字段变了、换存储引擎、旧客户端会失效 | 换 MySQL、`/api/sessions` 改路径 |
| **Y 次版本** | 新增功能 | 向后兼容：加了接口、加了页面、加了配置项 | 错题本、自测、导图 |
| **Z 修订号** | 缺陷修复 | 只改实现，契约不变 | 修复导出崩溃、修 SQL 参数 |

**口诀：加功能升中位，修 bug 升末位，破坏兼容才升首位。**

升高位后低位必须清零：`1.9.9` 升 minor → `1.10.0`（不是 `1.9.10`），升 major → `2.0.0`。

## 二、预发布与构建元数据

正式发布前用后缀标记，格式 `1.1.0-rc.1`、`1.1.0-beta.2`：

| 后缀 | 含义 | 能给别人用吗 |
| --- | --- | --- |
| `-alpha.N` | 内部联调，功能可能缺失 | 不能 |
| `-beta.N` | 功能齐了，还在修 bug | 可以给测试同学 |
| `-rc.N` | 候选发布，只等最终确认 | 可以给评审/助教 |

构建元数据用 `+` 追加，不参与排序：`1.1.0+20261119`。

## 三、本项目的版本线

| 版本 | 日期 | 内容 | 状态 |
| --- | --- | --- | --- |
| `1.0.0-rc.1` ~ `rc.4` | 10/20 – 10/23 | 合并队友代码、修导出与测试隔离 | 候选版 |
| **`1.0.0`** | 11/16 | 首个正式发布：单课程闭环 | 稳定基线 |
| `1.1.0` | 11/19 | 错题本 + 自测 + 图形化导图 | 开发中（`CHANGELOG` 的 Unreleased） |
| `1.1.x` | 之后 | 只修缺陷 | — |
| `2.0.0` | 待定 | 换 MySQL / 改接口契约 | — |

**为什么 1.0.0 不是 0.x**：SemVer 规定 `1.0.0` 表示「公开 API 已定义并稳定」。本项目 22 个接口在 10/20 定稿、写进设计说明书，10/24 起线上对外提供服务，之后只增不改，符合 1.0.0 的语义。

## 四、Git 标签与 Release

```bash
# 打标签（附注标签，带说明）
git tag -a v1.1.0 -m "错题本、智能自测、图形化思维导图"

# 推送标签（标签不会随 commit 自动推送）
git push origin main --tags

# 查看
git tag -l "v1.*" --sort=-v:refname
```

规则：

1. **标签必须带 `v` 前缀**（`v1.1.0`），与 GitHub Release 名称一致；
2. 标签打在 `main` 的发布提交上，**不要打在特性分支**；
3. Release 说明直接复制 `CHANGELOG.md` 对应段落，不要另写一份；
4. 发布包（zip）作为 Release 的附件上传，文件名带版本号与日期。

## 五、发版流程（每有大进展执行一次）

```bash
# 1. 确认要发的是哪一档
#    新功能 → minor；只修 bug → patch；不兼容 → major

# 2. 预览（不改文件）
python scripts/release.py --bump minor --dry-run

# 3. 正式发版（自动改 VERSION、写 CHANGELOG、打包）
python scripts/release.py --bump minor --notes "新增错题本、智能自测、图形化思维导图"

# 4. 提交并打标签
git add VERSION CHANGELOG.md
git commit -m "chore(release): v1.1.0"
git tag -a v1.1.0 -m "错题本、智能自测、图形化思维导图"
git push origin main --tags

# 5. 在 GitHub 上基于该 tag 建 Release，上传发布包
```

发版前必须全绿：

```bash
python -m pytest -q          # 当前 41 项
python scripts/e2e_smoke.py  # 端到端
python scripts/smoke_self_test.py
```

## 六、CHANGELOG 写法

按 `Keep a Changelog` 分六类：`新增`、`变更`、`废弃`、`移除`、`修复`、`安全`。

要点：

1. **`[Unreleased]` 永远在最上面**，日常开发往这里写，发版时整段落变成新版本号；
2. 每条写「对使用者有什么影响」，不写「改了哪个函数」；
3. 破坏性改动必须单独标注，并用一句话说明迁移方式；
4. 日期用 `YYYY-MM-DD`；
5. 版本间用 `---` 分隔。

反例（不要这样写）：

```
- 重构了 quiz.py 的判分逻辑          ← 说的是实现，不是影响
```

正例：

```
- 修复：交卷重复提交会导致错题次数翻倍（现在幂等，只记一次）
```

## 七、常见错误

| 错误 | 后果 | 正确做法 |
| --- | --- | --- |
| 用 `1.10` 与 `1.9` 比较时按小数比 | 误判 `1.9` 更新 | 按点分段比较，`1.10.0 > 1.9.0` |
| 修 bug 却升 minor | 版本线膨胀，看不出真实变更量 | 只改实现就升 patch |
| 加了功能却不升版本 | 出问题无法定位是哪一版 | 每完成一个可交付功能就发一次 |
| 标签打在特性分支 | 别人 checkout 不到完整状态 | 合入 main 后再打 |
| Release 说明与 CHANGELOG 不一致 | 两份真相 | Release 直接复制 CHANGELOG |
| 发布包里混入 `.env` / 数据库 | 密钥泄露、数据泄露 | 用 `scripts/make_v1_release.py`（内置排除与扫描） |

## 八、检查清单（发版前逐项打勾）

- [ ] 测试全绿（`pytest`、`e2e_smoke`、功能冒烟）
- [ ] `CHANGELOG.md` 的 Unreleased 已写清本次全部变更
- [ ] `VERSION` 与准备打的 tag 一致
- [ ] 发布包内不含 `.env`、`storage/*.db`、`.venv`、`__pycache__`
- [ ] 发布包能在干净环境跑起来（解压 → `bash deploy.sh`）
- [ ] 线上已部署该版本，并验证 `/api/health` 与首页
- [ ] GitHub Release 已上传发布包，说明引用 CHANGELOG
- [ ] 群里同步版本号与变更要点
